# Источник ожидаемого поведения

## Главное правило

`dev-social-frontend` — тестируемая система, а не эталон. Текущее состояние стенда может содержать известные и ещё не исправленные регрессионные дефекты. Успешное воспроизведение поведения на dev не делает это поведение правильным.

Dev-стенд разрешено использовать для:

- воспроизведения бага;
- поиска актуального DOM и технического локатора;
- получения trace, screenshot, console и network-диагностики;
- проверки того, исправлен ли уже зарегистрированный дефект.

Dev-стенд нельзя использовать как единственное основание для:

- изменения ожидаемого результата;
- удаления упавшей проверки;
- превращения дефекта в допустимое состояние;
- добавления нового бизнес-правила.

## Приоритет источников

Ожидаемый результат определяется в следующем порядке:

1. Утверждённые требования, acceptance criteria и решения владельца продукта.
2. Ожидаемые результаты старых Qase/Cypress-кейсов, если они не отменены новым требованием.
3. Зафиксированное правильное поведение из регрессионного отчёта или карточки дефекта.
4. Общие инварианты безопасности, прав доступа, сохранности данных и доступности.
5. Явно согласованная гипотеза, помеченная в тесте как требующая уточнения.

Текущее поведение dev-стенда в этот список не входит.

## Как оформлять расхождение

- Если правильное поведение известно, тест продолжает ожидать именно его и падает на дефекте.
- Если дефект уже зарегистрирован и его временно нельзя оставлять красным в общем прогоне, используется `test.fail` с причиной. Assertion всё равно описывает исправленное, а не фактическое поведение.
- Если правильное поведение неоднозначно, сценарий не закрепляется жёстким assertion до уточнения требования. Его можно оставить диагностическим и приложить наблюдения.
- После исправления бага `test.fail` удаляется; ожидаемый результат не переписывается.

## Локаторы и поведение разделены

DOM и названия компонентов могут меняться без изменения бизнес-смысла. Поэтому допустимо обновлять локатор после исследования dev-стенда, если assertion остаётся прежним.

Пример:

- старый XPath до кнопки «Удалить пост» заменяется на `getByRole('menuitem', { name: 'Удалить пост' })`;
- ожидаемый результат — исчезновение поста и состояние «Пост не найден» — остаётся требованием независимо от текущего бага на стенде.

## Новое покрытие сверх старого Cypress

Дополнительные проверки должны иметь понятный источник:

- security/accessibility invariant;
- ранее найденный регрессионный баг;
- подтверждённое бизнес-правило;
- диагностическая проверка без объявления текущего dev-поведения нормой.

Список из 95 регрессионных дефектов следует связать с тестами отдельно: для каждого дефекта нужны идентификатор, ожидаемое поведение, предусловия, приоритет и статус исправления.
