# Room tour проекта

## Ментальная модель

`package.json` выбирает тип запуска → `playwright.config.ts` создаёт браузерный проект → `auth.setup.ts` сохраняет сессию → fixture готовит каждую страницу → spec описывает пользовательский сценарий → page object выполняет повторяемые действия → reporter сохраняет доказательства.

## Карта папок

- `tests/<область>/*.spec.ts` — поведение продукта на языке пользователя.
- `tests/pages/` — повторяемые действия и локаторы конкретных экранов.
- `tests/fixtures/test.ts` — единая подготовка страницы: вход, системные баннеры, сетевой recorder.
- `tests/helpers/` — настройки окружения, уникальные данные, безопасная диагностика сети.
- `.auth/` — локальная сохранённая сессия; не попадает в Git.
- `test-results/` — screenshot, video, trace и контекст текущего прогона.
- `playwright-report/` — человекочитаемый HTML-отчёт.
- `docs/` — стратегия, результаты исследования, дефекты и инструкции.

## Почему устроено именно так

- Specs остаются короткими и читаются как сценарии, а технические детали живут в page objects.
- Локаторы строятся по ролям, именам и видимому тексту: это ближе к пользовательскому восприятию и одновременно проверяет доступность.
- Один worker выбран осознанно: SSO вращает refresh token, параллельные контексты одного пользователя конфликтуют.
- Mutation отделён тегом и переменной окружения, поэтому обычный `npm test` безопасен.
- Каждая изменяющая данные проверка уникально именует сущности и очищает их в `finally`.
- Ожидания проверяют состояние приложения, а не время. Поэтому нет `waitForTimeout`.
- Диагностика собирается при сбое, но секретные ключи в сетевых данных редактируются.

## Как читать тест

1. Начните с названия `describe` и `test` — это обещание сценария.
2. Найдите `page.goto` — исходный экран.
3. Действия через page object показывают пользовательский поток.
4. `expect` — проверяемый контракт.
5. В mutation-тесте найдите `try/finally` — гарантию очистки.

## Как добавить качественный тест

1. Опишите риск и ожидаемую ценность; не автоматизируйте сценарий только ради количества.
2. Выберите уровень: read-only UI, диагностический интеграционный или mutation E2E.
3. Подготовьте независимые данные с `uniqueMarker`.
4. Переиспользуемое действие вынесите в page object.
5. Используйте `getByRole`, `getByLabel`, `getByText`; CSS оставляйте для семантически недоступных web components.
6. Проверяйте наблюдаемый результат, а не внутреннюю реализацию.
7. Для mutation добавьте очистку в `finally` и проверьте удаление.
8. Запустите один тест, затем соответствующую группу, typecheck и полный безопасный набор.

## Критерии готовности теста

- понятное русское название;
- один бизнес-риск на тест;
- независимость от порядка запуска;
- нет фиксированных пауз и `force: true` без доказанной необходимости;
- нет секретов и постоянных тестовых данных в коде;
- падение объясняет проблему и оставляет артефакты;
- mutation всегда имеет безопасную очистку.
