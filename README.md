# Автотесты Social Frontend

TypeScript + Playwright. Тестируемый dev-стенд: `https://dev-social-frontend.sddt.efko.ru/`. Он не является источником ожидаемых результатов: требования берутся из тест-кейсов и подтверждений команды, а не из текущего поведения стенда.

Репозиторий: [github.com/StanL1ght/social-frontend-e2e](https://github.com/StanL1ght/social-frontend-e2e). Для запуска нужен доступ к корпоративному dev-стенду (возможно, VPN). Учётные данные в GitHub не хранятся.

## 1. Установить инструменты

1. Установите [Git](https://git-scm.com/downloads) и [Node.js 22 LTS](https://nodejs.org/). На Windows команды ниже выполняйте в PowerShell, на macOS/Linux — в терминале. VS Code не обязателен, но удобен для просмотра результатов.
2. Проверьте установку:

```bash
git --version
node --version
npm --version
```

Версия Node.js должна быть 22.x. Если команда не найдена, перезапустите терминал после установки.

## 2. Клонировать проект и установить зависимости

```bash
git clone https://github.com/StanL1ght/social-frontend-e2e.git
cd social-frontend-e2e
npm ci
npx playwright install chromium webkit
```

На Linux вместо последней команды используйте `npx playwright install --with-deps chromium webkit` — нужны системные библиотеки браузеров. После обновления проекта: `git pull` и `npm ci`.

## 3. Вписать секретные данные в локальный `.env`

Попросите у ответственного за тестовый стенд **две отдельные тестовые учётные записи** и URL тестовой группы. Первый пользователь должен управлять этой группой, второй — быть её участником. Используйте именно тестовые учётные записи: часть сценариев создаёт и удаляет записи, комментарии и группы. Не отправляйте пароли в чат, тикет или Git.

Скопируйте шаблон:

| Система | Команда |
|---|---|
| Windows PowerShell | `Copy-Item .env.example .env` |
| macOS/Linux | `cp .env.example .env` |

Откройте `.env` обычным текстовым редактором и замените значения:

```dotenv
BASE_URL=https://dev-social-frontend.sddt.efko.ru
E2E_EMAIL=логин_первого_тестового_пользователя
E2E_PASSWORD=пароль_первого_тестового_пользователя
E2E_MEMBER_EMAIL=логин_второго_тестового_пользователя
E2E_MEMBER_PASSWORD=пароль_второго_тестового_пользователя
E2E_MANAGED_GROUP_URL=https://dev-social-frontend.sddt.efko.ru/group/ID_ТЕСТОВОЙ_ГРУППЫ
E2E_MEMBER_CAN_PUBLISH=false
E2E_MENTION_QUERY=часть_имени_второго_пользователя
RUN_MUTATION_TESTS=false
```

Где взять значения:

- `E2E_EMAIL` / `E2E_PASSWORD` — вход первого тестового пользователя в Social Frontend. Именно им Playwright создаёт основную авторизованную сессию.
- `E2E_MEMBER_EMAIL` / `E2E_MEMBER_PASSWORD` — вход второго тестового пользователя, необходимый для ролей, подписок, реакций и других проверок между аккаунтами. Это **не** второй пароль первого пользователя.
- `E2E_MANAGED_GROUP_URL` — откройте заранее подготовленную группу первым пользователем и скопируйте полный адрес из браузера. Первый должен быть её владельцем или администратором, второй — участником. Пример формата указан выше; `ID_ТЕСТОВОЙ_ГРУППЫ` надо заменить реальным ID.
- `E2E_MEMBER_CAN_PUBLISH` — `true`, только если второму пользователю разрешено публиковать в этой группе; иначе `false`.
- `E2E_MENTION_QUERY` — короткая уникальная часть имени второго пользователя, по которой он находится при вводе `@`.
- `BASE_URL` меняйте только при согласованном запуске на другом стенде: часть API-помощников сейчас привязана к dev-backend, поэтому простая замена одного URL не гарантирует безопасную работу на другом окружении.

Если пароль содержит `#`, пробелы или `=`, заключите значение в двойные кавычки: `E2E_PASSWORD="пароль # 123"`. Не ставьте пробелы вокруг `=`. Не копируйте в `.env` строку `...` вместо реального значения. Файл `.env` и сохранённые сессии `.auth/` исключены из Git; проверка: `git status --short` не должен показывать `.env`.

Если второго пользователя или группы пока нет, оставьте соответствующие поля пустыми. Базовые однопользовательские тесты будут доступны, многоаккаунтные сценарии пропустятся. Для полного набора заполните все поля.

Проверьте вручную, что обе учётные записи входят на `BASE_URL` и стенд открывается с вашего компьютера. Пароли в README или командную строку не вписывайте.

## 4. Запустить тесты

| Задача | Команда | Что происходит |
|---|---|---|
| Первый безопасный запуск | `npm run test:smoke` | Короткая проверка входа, навигации и основных экранов без изменения данных. |
| Все проверки без изменения данных | `npm test` | Read-only набор на настроенных браузерах. |
| Критический путь | `npm run test:critical` | Выборочный desktop-прогон: навигация, поиск, мои публикации, создание/реакция/комментарий/удаление поста и создание/удаление группы. **Меняет тестовые данные.** |
| Все desktop-проверки без изменения данных | `npm run test:desktop` | Chromium, включая более широкий набор чтения. |
| Все проверки с изменением данных | `npm run test:mutation` | Создание/редактирование/удаление тестовых сущностей; может быть долгим. |
| Полный регресс | `npm run test:all` | Все проекты: desktop, mobile Chromium/WebKit, вход и многоаккаунтные проверки. **Меняет данные; может длиться долго.** |
| Отдельный мобильный прогон | `npm run test:mobile` | Выборочный адаптивный набор на Pixel 7/Chromium и iPhone 13/WebKit. |
| Только Android/Chromium | `npm run test:mobile:chromium` | Один мобильный движок. |
| Только iPhone/WebKit | `npm run test:mobile:webkit` | Один мобильный движок. |
| Только многоаккаунтные | `npm run test:multiuser` | Для меняющих данные сценариев дополнительно задайте `RUN_MUTATION_TESTS=true` (см. ниже). |
| Проверить TypeScript | `npm run typecheck` | Без браузера и запросов к стенду. |

`test:critical`, `test:mutation` и `test:all` сами включают `RUN_MUTATION_TESTS=true`. Для `test:multiuser` включите его на время команды:

```bash
# macOS/Linux
RUN_MUTATION_TESTS=true npm run test:multiuser
```

```powershell
# Windows PowerShell
$env:RUN_MUTATION_TESTS="true"
npm run test:multiuser
Remove-Item Env:RUN_MUTATION_TESTS
```

Перед любым прогоном с изменением данных убедитесь, что в `.env` указаны **тестовые** аккаунты и группа. Тесты стараются удалять созданные сущности через API/UI даже при падении, но после аварийного завершения очистка может не пройти. Остатки можно найти по префиксу `QA-E2E-`.

`npm run test:mobile` — не весь desktop-набор на маленьком экране. Он проверяет адаптивную навигацию, вкладки, поиск, редактор и отсутствие горизонтальной прокрутки. Подробное обоснование: [мобильная стратегия](artifacts/mobile-test-strategy.md).

## 5. Посмотреть результат и запустить один тест

После любого прогона:

```bash
npm run report
```

HTML-отчёт содержит ошибки и диагностические вложения; при падении сохраняются screenshot, video и trace в `test-results/`. Результаты и сессии не отправляются в Git.

Один файл, например:

```bash
npx playwright test tests/search/global-search.spec.ts --project=desktop-chromium
```

Перед запуском можно посмотреть, сколько сценариев выбрано, без обращения к стенду:

```bash
npx playwright test --list --project=desktop-chromium --grep @critical
```

Для теста, который меняет данные, используйте соответствующий npm-скрипт или включите `RUN_MUTATION_TESTS=true`. При первом авторизованном запуске setup создаст локальный файл `.auth/user.json`. Если он устарел, повторный setup обновит его.

## Покрытие тест-кейсов

Актуальная сводка по новому экспорту: [отчёт по покрытию](docs/COVERAGE-EXPORT-2026-09-30.md) и [поимённая матрица](artifacts/coverage-export-2026-09-30.json). При подсчёте исключён только раздел «Устаревшее»; кейсы `deprecated` в других разделах включены, как и просил владелец проекта. Статический зачёт покрытия не равен результату сегодняшнего полного прогона.

Для обновления отчёта по следующему экспорту укажите путь к JSON:

```bash
node tools/audit-new-case-export.mjs /путь/к/новому-экспорту.json
node tools/build-export-coverage.mjs /путь/к/новому-экспорту.json
```

Новый экспорт надо положить локально: он не входит в репозиторий. Если состав/шаги кейсов изменятся, классификацию в `tools/build-export-coverage.mjs` нужно пересмотреть, а не механически считать ID в тестах полным покрытием.
