# Кейсы соцсети

Этот навык применяется к работе с тест-кейсами проекта `social-frontend-e2e`, включая отдельный новый кейс, замену старого, отчёты о покрытии и JSON для импорта.

1. До формулировки кейса прочитай актуальную общую базу. Основная копия в проекте: `artifacts/Все кейсы — точечная актуализация.json`; если пользователь предоставил более свежий экспорт, сравни его и используй свежий источник. Найди существующие кейсы по смыслу, ключам и сьютам, включая черновики без `id`/`key`. Проверь относящиеся к теме новые и заменённые кейсы в `artifacts/`. Если пользователь ссылается на соседнюю задачу, прочитай её через инструменты задач, когда она доступна.
2. Не выводи ожидаемый результат из одного лишь поведения dev-стенда. Разделяй подтверждённое пользователем требование, существующий кейс, наблюдение на стенде и предположение. Не смешивай независимые цели проверки в один кейс. Если идентичный кейс уже существует, не добавляй дубль молча: обнови, замени или объясни связь.
3. Для импортного JSON используй подтверждённую структуру общего экспорта: корневые `schema_version`, `project`, `selection`, `summary`, `suites`; внутри нужного сьюта — `id`, `title`, `path`, `position`, `test_cases`, `suites`; у кейса — поля и `steps` того же вида, что в рабочем файле `artifacts/Уведомления, заявки, опросы и роли — для импорта с пометками.json`. Не выдавай корневой `new_test_cases`, `replacement_cases` или список только изменённых шагов как импортируемый файл.
4. Для нового кейса не копируй старые `id`/`key`; в заголовке используй `[НОВЫЙ]`. Для полной замены — `[ЗАМЕНА ESN-…]`, исходный ключ также укажи в описании. Если API позволяет обновить старый кейс на месте, сохраняй его `id` и сьют: отдельной устаревшей версии не возникает. Если замена создаётся отдельной записью, прежний кейс переноси в существующий сьют системы тестирования «Устаревшее», не удаляй. Неактуальные кейсы без замены тоже переноси в «Устаревшее». Черновик без ключа идентифицируй исходным названием и сьютом. Не добавляй поля, которые не подтверждены рабочим образцом импорта.
5. Даже для одного кейса создавай полный экспорт с одним сьютом и одной записью `test_cases`. Проверяй не только синтаксис JSON, но и форму, счётчики, число шагов, отсутствие лишних кейсов и соответствие нужному сьюту. Запускай `node tools/validate-case-import.mjs <файл>` и дополнительно сверяй итог с рабочим образцом; фактический импорт не утверждай без проверки в системе.
6. В ответе называй статус точно: кейс описан, файл структурно проверен, импорт подтверждён или не подтверждён, автотест работает или пока нет. Давай ссылку именно на соответствующий файл, а не на сборник с другими кейсами.
